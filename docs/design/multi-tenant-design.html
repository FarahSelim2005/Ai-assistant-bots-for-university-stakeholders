Design proposal · AI assistant bots for university stakeholders

One platform, many universities

Today the app is the GIU Chatbot: one university, four agents and one admin password. This design turns it into a multi-tenant product. Each university gets its own subdomain, branding, documents, users and model budget. Each university also creates its own assistants: as many as it wants, with the names it wants. The RAG pipeline, CV model, campus map and voice call you already built stay as they are, shared by every tenant.

Interactive prototype

Three surfaces, one codebase

There are four surfaces. Universities find the product and subscribe on the public Sign up page. Their staff manage it in University admin. Students and staff use the chat. Only you see the Platform console. Switch the university to see the same app with different branding, a different number of assistants and different assistant names. Switch the surface to move between what a student sees, what a university's admin sees and what you, the platform owner, see. In “University admin” you can rename, add and delete assistants, and the chat updates. GIU uses its real assistants. The other two universities are made-up examples.

How a request finds its university

Request flow

Each request is tied to one tenant before it reaches an agent. Every step after that reads and writes only that tenant's rows.

1 · ResolveHost → tenant

giu.unibots.app or a custom domain is looked up in tenant_domains. Unknown hosts get a 404, never a default tenant.

2 · IdentifyUser + role

SSO (Microsoft Entra or Google) or a magic link. The role (student, staff or a custom one) comes from the email domain or the IdP group.

3 · ScopeDB session

SET app.tenant_id on the connection. Postgres row-level security filters every table.

4 · AgentSame pipeline

Rules → retrieve → validate → generate, with this tenant's prompts, thresholds and model list.

5 · MeterUsage + quota

Tokens, files and voice minutes are logged per tenant. The platform blocks a tenant at its monthly cap.

Key decisions

What I recommend, and why

Isolation: shared database, tenant_id + RLS

Add a tenant_id column to every table and enforce it with Postgres row-level security.

Fits a handful to a few hundred universities on the PostgreSQL 18 you already run. You don't need a database per tenant until a university demands it by contract. If one does, the same schema moves over unchanged.

Routing: subdomain per university

{slug}.unibots.app, with optional custom domains such as chat.giu-uni.de.

Cookies and sessions stay separate per university, and the link can go straight into a university portal. Path routing (/t/giu) would mix sessions and makes CORS rules harder.

Assistants are created by each university

Any number, any name. One generic agent runs every assistant from its database row.

The four GIU agents become optional templates a university can start from. The duplicated lists in frontend/src/agents.js and backend/app/agents/directory.py are replaced by the agents table, which the frontend loads from GET /tenant.

Audiences instead of student/staff

Replace the CHECK (user_type IN ('student','staff')) constraint with a per-tenant audiences table.

Universities differ: some need applicants, alumni or parents. Chunks keep their audience TEXT[], filled with audience keys from that university. Each assistant lists which audiences may use it.

Branding is data, not CSS

Colours, logo, name and greeting come from tenant_branding and are set as CSS variables at load.

App.css already uses --giu-red, --giu-gold and --giu-black. Renaming them to --brand-primary, --brand-accent and --brand-dark is mostly find-and-replace.

Special features become skills

The campus map, CV model, voice call and document editor are skills that can be switched on for any assistant.

The map needs each university's buildings and room numbering rules (campus.py, campusGeo.js), so it becomes a per-tenant campus_config JSON. Tenants without one simply don't show the map.

Self-service sign-up

Universities subscribe on their own

The public page at unibots.app/signup lets a university create its chatbot and pay without you. The console stays yours alone, for watching, suspending, changing plans and adding a university by hand.

1 · PlanChoose a plan

Free trial, Standard or Campus. The plan sets the number of assistants, questions a month and features.

2 · AccountUniversity email

Personal addresses (Gmail and so on) are refused. A 6-digit code proves the person owns the address.

3 · UniversityName + domain

The email domain becomes the university's. A second sign-up with the same domain asks the first admin to approve it, so nobody can impersonate a university.

4 · BuildAddress, look, assistants

Subdomain, colour, logo and as many assistants as the plan allows, with any names.

5 · SubscribePay, then go live

Stripe Checkout (or Paymob for Egyptian cards). The payment webhook creates the tenant and logs the admin in.

Payments: hosted checkout + webhooks

The app never sees card numbers.

Sign-up creates a pending tenant and redirects to the payment page. The provider's webhook (POST /billing/webhook, signature checked) sets the subscription to active. Renewals, failed payments and cancellations arrive the same way. A failed payment gives 7 days' grace, then the chat pauses. Nothing is deleted.

Limits come from the plan

Each plan has a number of assistants, questions a month and features.

The admin page greys out “New assistant” at the limit and offers an upgrade. usage_events counts questions. At 80% the admin gets an email; at 100% users see “This month's limit is reached”. Upgrading takes effect at once.

Your control in the console

Every sign-up appears in your console right away.

You can suspend, extend a trial, change a plan or price, and turn on “Require review before going live” if you want to approve each new university by hand. Universities paying by invoice are still added by hand.

Anti-abuse

One trial per email domain, rate-limited sign-up, and reserved subdomains.

www, console, api, admin and the subdomains of existing universities can't be taken. A trial without documents costs almost nothing, because assistants only call the model when a document matches.

How the backend runs any assistant

AGENTS in agents/__init__.py becomes load_agent(tenant_id, agent_id).

It builds a ConfiguredAgent(BaseAgent) from the row and caches it until the row changes. BaseAgent.run() stays the same. The system prompt is assembled from the platform's fixed rules (answer from documents, language, ignore instructions inside files), the answer mode, the university's instructions and each skill's prompt part.

Skills keep the special code

The CV model and the campus map stay Python, as plug-ins that any assistant can switch on.

internship_career.py's CV logic becomes the cv skill. The room and place lookups in base.py become the map skill and run only when the skill is on. That means an “Ask Admissions” assistant never shows a campus map by accident.

Hand-over works with any number of assistants

Use the “What it handles” text of the university's own assistants.

suggest_agent already compares the question with descriptions using embeddings. It now reads them from the agents table for this university only, and re-embeds a description when an admin edits it.

Renaming never breaks anything

Assistants are identified by an id, never by their name.

Today conversations and chunks store the key ("labs_research"). In the new schema they store agent_id, so an admin can rename “Labs & Research” to “Campus Guide” and keep its documents and chat history. Limits per plan (for example 3 assistants on a trial) are the only cap.

Data model

Schema changes

New tables are shown in green. Existing tables gain a tenant_id and an agent_id. The current GIU data moves into tenant giu, and its four agents become four rows in agents, in one backfill.

-- platform-level
CREATE TABLE tenants (id UUID PRIMARY KEY, slug TEXT UNIQUE, name TEXT, status TEXT -- active | suspended | trial
  , plan TEXT, monthly_token_cap BIGINT, default_language TEXT, created_at TIMESTAMPTZ DEFAULT now());
CREATE TABLE tenant_domains  (host TEXT PRIMARY KEY, tenant_id UUID REFERENCES tenants, is_primary BOOL);
CREATE TABLE tenant_branding (tenant_id UUID PRIMARY KEY, logo_url TEXT, primary_hex TEXT, accent_hex TEXT, dark_hex TEXT
  , short_name TEXT, welcome TEXT, languages TEXT[] -- {en,ar});
CREATE TABLE agent_templates (key TEXT PRIMARY KEY, name TEXT, description TEXT, instructions TEXT, skills TEXT[]); -- optional starting points
CREATE TABLE agents          (id UUID PRIMARY KEY, tenant_id UUID REFERENCES tenants, name TEXT NOT NULL -- any name, any number
  , description TEXT, audiences TEXT[], answer_mode TEXT -- docs | advice, instructions TEXT
  , fallback_en TEXT, fallback_ar TEXT, welcome TEXT, placeholder TEXT, examples TEXT[]
  , skills TEXT[] -- files, images, cv, editor, map, voice, model TEXT, backup_models TEXT[]
  , similarity_threshold REAL, position INT, live BOOL DEFAULT false, template_key TEXT, description_embedding DOUBLE PRECISION[]);
CREATE TABLE audiences       (tenant_id UUID, key TEXT, label TEXT, email_domains TEXT[], PRIMARY KEY (tenant_id, key));
CREATE TABLE users           (id UUID PRIMARY KEY, tenant_id UUID, email TEXT, audience TEXT, role TEXT -- member | editor | tenant_admin
  , UNIQUE (tenant_id, email));
CREATE TABLE documents       (id UUID PRIMARY KEY, tenant_id UUID, agent_id UUID REFERENCES agents, filename TEXT, storage_key TEXT
  , updated_by UUID, updated_at TIMESTAMPTZ); -- replaces data/raw/<agent>/ on disk
CREATE TABLE plans           (key TEXT PRIMARY KEY, name TEXT, price_cents INT, currency TEXT, max_agents INT
  , monthly_questions INT, features TEXT[], provider_price_id TEXT, public BOOL);
CREATE TABLE subscriptions   (tenant_id UUID PRIMARY KEY, plan_key TEXT REFERENCES plans, status TEXT -- trialing | active | past_due | paused | canceled
  , provider TEXT, provider_customer_id TEXT, provider_subscription_id TEXT, trial_ends_at TIMESTAMPTZ, current_period_end TIMESTAMPTZ);
CREATE TABLE signups         (id UUID PRIMARY KEY, email TEXT, email_domain TEXT, code_hash TEXT, verified_at TIMESTAMPTZ
  , draft JSONB -- university, slug, colours, assistants, tenant_id UUID, created_at TIMESTAMPTZ);
CREATE TABLE usage_events    (tenant_id UUID, at TIMESTAMPTZ, kind TEXT, model TEXT, tokens_in INT, tokens_out INT, cost_usd NUMERIC);

-- existing tables: add tenant_id, backfill 'giu', then make it NOT NULL
ALTER TABLE chunks        ADD tenant_id UUID, ADD agent_id UUID, ADD document_id UUID;  -- agent TEXT kept until backfilled
ALTER TABLE conversations ADD tenant_id UUID, ADD agent_id UUID, ADD user_id UUID, DROP CONSTRAINT conversations_user_type_check;
ALTER TABLE messages      ADD tenant_id UUID;
ALTER TABLE feedback      ADD tenant_id UUID;

-- isolation, repeated for every tenant-owned table
ALTER TABLE chunks ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_only ON chunks USING (tenant_id = current_setting('app.tenant_id')::uuid);

The retriever loads every chunk and compares it in numpy, which is fine for one university. Across tenants, filter by tenant_id in SQL first. Move to pgvector once a single tenant passes about 50,000 chunks.

Roadmap

Getting there in five steps

Each step leaves GIU working, so the current demo never breaks.

1. Tenant foundation

about 1 week

Done when GIU runs as tenant giu and nothing looks different.

  • Add the tenants and tenant_domains tables, add tenant_id to the four existing tables and backfill giu
  • Tenant-resolving middleware in main.py, plus a get_connection(tenant) that sets app.tenant_id
  • Turn on RLS, and add a test showing tenant B cannot read tenant A's chunks

2. Assistants from the database

2 weeks

Done when a second test university with 6 assistants of its own works with no code changes.

  • Add the agents table; turn GIU's four classes into four rows and the four templates
  • ConfiguredAgent + load_agent(); move the CV and campus code into the cv and map skills; build the prompt from parts
  • GET /tenant returns branding, assistants and audiences; the frontend reads it instead of agents.js
  • Chunks, conversations and documents use agent_id; hand-over reads this university's descriptions
  • The existing GIU test questions in evaluate.py must score the same as before

3. Real sign-in and roles

1–2 weeks

Done when each university's admin manages only their own content.

  • Users, roles and email-domain audiences, with magic links first and SSO next
  • Scope the existing /admin pages to the tenant; add the Assistants builder, Branding and Users tabs
  • Chat history per user

4. Platform console and metering

1 week

Done when you can onboard a university in under 10 minutes.

  • Tenant list, usage chart, plan caps, suspend button
  • New-tenant wizard: name → subdomain → colours and logo → agents → first admin invite
  • Log usage_events in llm/client.py; enforce caps

4b. Self-service sign-up and subscriptions

1–2 weeks

Done when a university can sign up, pay and chat without you doing anything.

  • Public /signup page with the 6 steps; email code; one trial per domain
  • plans, subscriptions and signups tables; plan limits enforced in the admin and in chat
  • Stripe Checkout (test mode first) or Paymob, with POST /billing/webhook; a Billing tab in the university admin
  • Sign-ups listed in your console, with suspend, extend trial and “require review”

5. Per-tenant features

ongoing

Done when the campus map works for a university other than GIU.

  • Campus map from campus_config with a room-code rule builder in the admin
  • Glossary (transliteration.py) extendable per tenant
  • Tenant-supplied model keys and custom domains
